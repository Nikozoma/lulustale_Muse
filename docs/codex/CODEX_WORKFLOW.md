# Codex Workflow

## Outcome-Oriented Default

Use this sequence:

`UNDERSTAND → INSPECT → IMPLEMENT COHERENT BATCH → MINIMAL TARGETED SANITY CHECK → MAKE RUNNABLE → USER TESTS → BATCH FIXES`

Understand the requested outcome and protected behavior first. Inspect only enough active evidence to establish the relevant contract. Then implement one coherent correlated batch that leaves the project in a runnable, reviewable state.

Do not fragment a clear reversible task into approval-heavy micro-steps. Do not broaden a focused request into cleanup, refactoring, future systems, or infrastructure work.

## Lean Validation

Before a nontrivial check, ask: **Will the result materially affect what I do next?**

- Use the smallest check that can reveal a relevant implementation error.
- Run focused type, unit, schema, or asset checks only when the task can affect those contracts.
- Do not run a full suite, broad regression sweep, production build, repeated validator loop, benchmark, parity proof, or artifact comparison merely because work finished.
- Do not automate gameplay navigation or manufacture device/visual approval.
- If the user will perform the decisive visual/gameplay review, make the work runnable and provide a short review target.

Human eyes and hands are the final authority for animation feel, art, UI, mobile ergonomics, collision feel, foreground behavior, gameplay pacing, and other subjective outcomes.

## Planning and Goal Autonomy

In planning, choose and continue with a clearly recommended reversible option unless it materially changes architecture, risks migration/data/compatibility, creates high rework, or depends on unresolved subjective preference.

For goal/outcome work:

- continue through routine reversible implementation choices;
- stop for missing real assets/data/authority instead of inventing substitutes;
- preserve explicit approval and publication gates;
- report a genuine blocker precisely;
- do not redefine the outcome merely to declare completion.

## Working Trees and Git

Assume existing modifications belong to the user. Inspect status before meaningful edits, preserve unrelated changes, and avoid overlapping them where possible.

Do not reset, clean, stash, revert, discard, commit, branch, push, or create Git checkpoints unless explicitly requested. A dirty tree is not a request for housekeeping.

## Artifact-First Work

When the deliverable is an artifact—documentation, sprite sheet, manifest, map bundle, report, or packaged output—make the artifact itself the primary result. Use supporting prose and validation only to make it understandable and safely reviewable.

Use real project inputs and current authority. Preserve provenance and earlier useful revisions instead of silently overwriting or reconstructing them.

## Calibration

Use a representative calibration gate only when establishing a genuinely uncertain or fragile baseline, such as new animation mechanics, sub-tile collision feel, foreground handoff, or phone-scale presentation.

Once the representative baseline is explicitly approved, expand in coherent production batches. Do not keep baby-stepping established mechanics or repeatedly re-proving the same baseline.

Passing deterministic checks can establish structural readiness. It cannot replace human approval of subjective quality.
